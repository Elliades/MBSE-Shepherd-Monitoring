AI Follows the MBSE Method: from the Shepherd Drone to the Swarm

L’IA suit la démarche MBSE : du drone berger à l’essaim

A written method, a Kotlin generator, and simulation as the judge. The LLM does not “draw” an architecture: it decides with the engineer, generates, gets checked, replays the mission, and iterates.

Une méthode écrite, un générateur Kotlin, et la simulation pour juge. Le LLM ne « dessine » pas une architecture : il décide avec l’ingénieur, génère, se fait contrôler, rejoue la mission et itère.

Quentin Cespédès · November 2026

Quentin Cespédès · novembre 2026

The first two articles built three things for our students: a method, automation in Cameo, and a judge, the mission scenarios replayed in simulation. An LLM does exactly three things well: follow a written method, call tools, iterate on a test result. So we gave it the course.

The method runs through three layers, lifecycle (the operational layer), functional and logical, and the requirements run through all of them. Each element of a layer is linked to the one it comes from, so the validator can follow any requirement end to end:

Les deux premiers articles ont construit trois choses pour nos étudiants : une démarche, de l’automatisation dans Cameo, et un juge, les scénarios de la mission rejoués en simulation. Un LLM sait faire exactement trois choses : suivre une méthode écrite, appeler des outils, itérer sur un résultat de test. On lui a donc donné le cours.

La méthode traverse trois couches, cycle de vie (la couche opérationnelle), fonctionnelle et logique, et les exigences les traversent toutes. Chaque élément d’une couche est relié à celui dont il vient : le validateur peut suivre n’importe quelle exigence de bout en bout.

1 Define the mission: requirements, scenarios, state machine

1 Définir la mission : exigences, scénarios, machine d’états

No vibe-modeling. If the AI wrote its own scenarios and its architecture, it would grade its own homework. The engineer sets the intent: context, mission phases, requirements and acceptance scenarios (nominal, alternative, dysfunctional). The LLM proposes the decision tables; nothing is written in Cameo until a human has validated them.

The mission then becomes one state machine, driven by the very signals of the lifecycle scenarios. Each mode runs a service function. The scenarios are played on it, and together they must take every branch: a branch nobody reaches is either a missing scenario or a dead branch. Play them:

Pas de vibe-modeling. Si l’IA écrivait ses scénarios et son architecture, elle corrigerait sa propre copie. L’ingénieur pose l’intention : contexte, phases de la mission, exigences et scénarios d’acceptation (nominal, alternatif, dysfonctionnel). Le LLM propose les tables de décision ; rien n’est écrit dans Cameo tant qu’un humain ne les a pas validées.

La mission devient alors une machine d’états, menée par les signaux mêmes des scénarios du cycle de vie. Chaque mode exécute une fonction de service. Les scénarios se jouent dessus, et ensemble ils doivent prendre toutes les branches : une branche que personne n’atteint, c’est un scénario qui manque ou une branche morte. Jouez-les :

3 Generate the architecture: a Kotlin script, the tools of the method

3 Générer l’architecture : un script Kotlin, les outils de la méthode

Let an LLM build a logical architecture element by element through MCP calls, and it burns its context window on plumbing, loses its identifiers, and fails. So it does not. It writes one Kotlin file, in the vocabulary of the method: components, allocations, the signal table, the context. Each decision of a validated table becomes one line.

The engine does the rest with the very right-clicks of the second article, called from code: Logical Transition, Delegate to external systems, Create All Missing Signal Ports, Merge Ports, Auto Connect. Then plan shows what will change, apply writes it, and a second plan must find nothing left to do.

Laissez un LLM construire une architecture logique élément par élément à coups d’appels MCP : il brûle sa fenêtre de contexte en plomberie, perd ses identifiants, et échoue. Il ne le fait donc pas. Il écrit un fichier Kotlin, dans le vocabulaire de la méthode : composants, allocations, table des signaux, contexte. Chaque décision d’une table validée devient une ligne.

Le moteur fait le reste avec les clics droits mêmes du deuxième article, appelés depuis le code : Logical Transition, Delegate to external systems, Create All Missing Signal Ports, Merge Ports, Auto Connect. Puis plan montre ce qui va changer, apply l’écrit, et un second plan ne doit plus rien trouver à faire.

4 Verify, then iterate

4 Vérifier, puis itérer

One validator, one verdict: PASS, FAIL or INCOMPLETE. It stacks the checks from the cheapest to the most expensive: the Kotlin compiler, the method rules on the description before anything is written, idempotence, the SysML validation of Cameo on the model read back, the method rules (traceability and completeness: every mode has an owner, every function is allocated, every requirement is verified), then the simulation of the scenarios, their coverage and their measures.

When a scenario fails, the LLM must decide who is wrong. The expectations come from the lifecycle scenarios, never from the generated model: copying the observed states into the scenario to turn it green is forbidden. Here is a real failure, replayed live:

Un validateur, un verdict : PASS, FAIL ou INCOMPLETE. Il empile les contrôles du moins cher au plus cher : le compilateur Kotlin, les règles de méthode sur la description avant toute écriture, l’idempotence, la validation SysML de Cameo sur le modèle relu, les règles de méthode (traçabilité et complétude : chaque mode a un propriétaire, chaque fonction est allouée, chaque exigence est vérifiée), puis la simulation des scénarios, leur couverture et leurs mesures.

Quand un scénario échoue, le LLM doit décider qui a tort. Les attendus viennent des scénarios du cycle de vie, jamais du modèle généré : recopier les états observés dans le scénario pour le faire passer au vert est interdit. Voici un vrai échec, rejoué en direct :

5 Scenarios as measuring instruments

5 Les scénarios comme instruments de mesure

A scenario that passes is a verdict. A scenario that runs is also a measure. The same replay gives the numbers the trade-off promised: messages, length of the reaction chains, load on the busiest component, states actually reached. The estimates of Figure 3 must agree with them; a large gap reopens the trade-off.

Un scénario qui passe, c’est un verdict. Un scénario qui tourne, c’est aussi une mesure. Le même rejeu donne les chiffres que le trade-off promettait : messages, longueur des chaînes de réaction, charge du composant le plus sollicité, états réellement atteints. 6 And now, the swarm

6 Et maintenant, l’essaim

A bear on one side, a stray sheep on the other: one drone is no longer enough. The golden rule becomes a driver: the flock is never left without a drone. The mission does not change; the allocation does (roles, a master on the ground or in the air), and so do the signal table and the scenarios’ expectations. The same method, the same generator, the same judge.

Un ours d’un côté, une brebis égarée de l’autre : un seul drone ne suffit plus. La règle d’or devient un driver : le troupeau n’est jamais laissé sans drone. La mission ne change pas ; l’allocation, si (des rôles, un maître au sol ou en vol), et avec elle la table des signaux et les attendus des scénarios. La même méthode, le même générateur, le même juge.

7 Bilan

The same toolsthe plugin’s right-clicks, called from one Kotlin file instead of hundreds of calls.

Under the hood

Sous le capot

The method, as the LLM reads it

A skill, mbse-architecture: one sheet per layer (requirements, lifecycle, functional, logical), plus traceability, Kotlin and testing. Each sheet gives the concepts, the steps with their reasoning, the decision tables and the rules as ids (LC-01…, FN-01…16, LG-01…25, TR-01…19). The rules are code, one class per rule, and the same code judges the LLM’s description, the model it wrote, and a student’s model.

The engine: describe, plan, apply, read back

The generator describes; the engine reconciles instead of rebuilding. It owns a scope, computes a plan (CREATE, UPDATE, REBUILD, EXTRA), writes in one undoable session, derives what has a single answer (ports, conjugation, _ext signals, connectors, «refine» / «allocate», layout), then reads the model back and runs the rules again. A project’s generators live in their own project, loaded as a jar, never in the plugin.

The validator and its profiles

Profiles layer:, gate:, trace, delivery. A rule whose input is missing is skipped, never passed: hence INCOMPLETE. Accepted exceptions are waive(rule, element, because, by) lines in the generator, with a reason and an author. The same verdict is reachable from MCP, from a validation suite in Cameo, from the command line, and from a side service that reads an exported model without Cameo.

La méthode, telle que le LLM la lit

Un skill, mbse-architecture : une fiche par couche (exigences, cycle de vie, fonctionnel, logique), plus la traçabilité, Kotlin et les tests. Chaque fiche donne les concepts, les étapes avec leur raisonnement, les tables de décision et les règles, numérotées (LC-01…, FN-01…16, LG-01…25, TR-01…19). Les règles sont du code, une classe par règle, et le même code juge la description du LLM, le modèle qu’il a écrit et le modèle d’un étudiant.

Le moteur : décrire, planifier, appliquer, relire

Le générateur décrit ; le moteur réconcilie au lieu de reconstruire. Il possède un périmètre, calcule un plan (CREATE, UPDATE, REBUILD, EXTRA), écrit en une session annulable, dérive ce qui n’a qu’une réponse (ports, conjugaison, signaux _ext, connecteurs, «refine» / «allocate», mise en page), puis relit le modèle et rejoue les règles. Les générateurs d’un projet vivent dans leur propre projet, chargés en jar, jamais dans le plugin.

Le validateur et ses profils

Profils layer:, gate:, trace, delivery. Une règle dont l’entrée manque est sautée, jamais réussie : d’où INCOMPLETE. Les exceptions acceptées sont des lignes waive(rule, element, because, by) dans le générateur, avec une raison et un auteur. Le même verdict s’obtient depuis MCP, depuis une suite de validation dans Cameo, en ligne de commande, et depuis un service à côté qui lit un modèle exporté, sans Cameo.
